Operating an Autonomous Coding Agent Under Human Control

Joan Llompart
Engineering, DoD-contractor environment · 2026
How I used an AI coding agent to make real changes to a production system, with a control setup built so a human approved every consequential step, every phase could be rolled back, and nothing was reported done until it was verified. Written up to the standard our compliance work expects.

Note. This is a generalized writeup. All environment-identifying details (addresses, hostnames, accounts, organization) have been removed. It describes the method and safety posture, not the protected system.

Context

A small internal engineering environment runs a handful of self-hosted, open-source services (a Git server, a low-code database, a workflow-automation tool, and two internal web apps) on a single Windows host using Docker. The environment is governed by a U.S. defense-contractor security framework (CMMC Level 2): deny-by-default network firewall, host firewall, full-disk encryption at rest, managed-device compliance, and no inbound internet access — strictly LAN-only.

I own the security engineering and change control for this environment. In 2026 I used an AI coding agent as the executor for a complex, multi-phase production change, while keeping myself as the controller who scoped, approved, and verified every consequential step.

What the agent did, and what I kept under human control

The flagship change was an overnight, ~7-phase upgrade-and-integration of the Git server (version upgrade with a live database migration, reverse-proxy integration, backup-pipeline changes, and auto-generation of compliance evidence). The agent did the mechanical work fast and consistently; I designed the operation so that no step could cause unrecoverable harm without a human in the loop.

The control mechanisms I built around the agent:

  • Human checkpoints at every consequential boundary. The agent paused for explicit operator approval before each phase that touched live data, network exposure, or service availability. Autonomy was bounded, not open-ended.
  • Reversibility by default (limit the blast radius). Before any change: full database dump, configuration snapshot, and the prior binary/image were preserved as labeled rollback artifacts. Every phase had a tested “rename-old-back-and-restart” rollback path.
  • Pre-flight gating. The operation refused to start until automated checks confirmed all paths, services, dependencies, and connectivity were healthy — the agent could not begin work on an unsafe baseline.
  • Verify, then claim. After each phase, all services were regression-checked (every endpoint confirmed responding) before the agent was allowed to proceed or report success. Success was asserted only against observed output.
  • Least exposure. The container topology was designed so exactly one service publishes a single port; every other service is reachable only through an internal reverse proxy on an isolated bridge network — no container can reach the physical LAN directly or bypass the host/firewall boundary.

Security judgment beyond the agent

The same engagement produced a written update-management standard that I think is the most safety-relevant artifact, because it’s about resisting the easy-but-dangerous default:

  • No auto-update; pin everything by digest. Mutable tags (:latest, :stable) are banned in production because they silently ingest whatever upstream last pushed — including a compromised push. Exact image digests are recorded so any change is diffable and reproducible.
  • Supply-chain verification before any update. Checksum/signature checks against an independent source, changelog review for unexpected new network behavior, and a deliberate wait period after release (most supply-chain compromises surface in the first 48 hours).
  • Acting on a live incident. When a widely-used container-vulnerability scanner was itself compromised through its distribution channel (a 2026 supply-chain incident), I suspended adoption of that class of tooling and documented compensating controls — rather than reflexively adding a security tool that had just become an attack vector.

Why this generalizes to AI safety engineering

Running an autonomous agent against production showed me what AI control looks like as an actual engineering problem:

  • The hard part isn’t getting the agent to act — it’s bounding authority so a human can understand, approve, and reverse every consequential action, and so the agent cannot succeed at the wrong thing quietly.
  • An agent’s own tools and dependencies are an attack surface. The same supply-chain discipline I apply to container images applies to the tooling we hand autonomous agents.
  • Reversibility, pre-flight gating, and verify-before-claim are concrete, testable control primitives. They get harder to enforce as the agent gets more capable, which is exactly when you need them most.

Honest scope statement

I scoped, sequenced, approved, and verified this work; the AI agent executed under those controls. I am presenting the method and safety posture as my own work and judgment. Outcomes (all phases passed, all services verified, zero rollback invocations needed) are drawn from the operation’s own logs and post-change verification.
